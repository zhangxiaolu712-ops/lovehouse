## 4. 当前服务住户表

```text
用户 / Web / 未来 Android App
        ↓ HTTPS
Nginx :80 / :443
        ├─ 静态前端 → /root/lovehouse-dist
        ├─ /api/codex/* → Codex Chat sidecar :3002
        └─ /api/* + OAuth / MCP → Bridge :3000
                                      ├─ Claude Chat sidecar :3003
                                      ├─ Memory V2
                                      ├─ Engineering Workspace
                                      ├─ LivingRoom
                                      ├─ Project Checklist
                                      └─ Supabase / Provider adapters
```

当前现场监听：

| 端口 | 住户 | 边界 |
|---|---|---|
| 80 / 443 | Nginx | 公网入口 |
| 3000 | LoveHouse Bridge | Client API、OAuth、MCP、LivingRoom、Memory / Engineering 编排 |
| 3002 | Codex Chat sidecar | loopback 独立聊天 runtime |
| 3003 | Claude Chat sidecar | loopback 独立聊天 runtime |

Codex / Claude sidecar 与 Bridge 保持独立，不因为“方便”合并成一个大进程。

## 5. 前端与后端边界

前端为 React + Vite + HashRouter。

普通低风险业务模块在 Auth + RLS 边界清楚时，可以通过各自 service 使用 Supabase 客户端；高权限、跨服务和系统级能力由 Bridge / 后端承载。

当前主要后端能力：

- Bridge Client API：统一 Owner bearer、高权限操作、跨服务编排。
- Codex Chat / Claude Chat：独立 sidecar，通过 Bridge 或各自稳定入口接入。
- Memory V2：当前记忆主链。
- Engineering Workspace：长期工程事实、revision、source evidence 与工程待办；与生活 Memory 分离。
- Project Checklist：工程域持久状态，不依赖浏览器 localStorage 作为 canonical truth。
- Supabase：Auth + PostgreSQL；前端不得持有 service role / secret。

## 6. 模块和扩展口

模块之间保持低耦合，但不要把未来扩展口封死。

- 已知未来会增加的空间 / provider / 原生能力，优先通过稳定接口“接入”，不为每个新能力重新造一套系统。
- `shared` 适合类型、常量、schema、纯函数、无状态工具；不放跨模块可变单例。
- 各业务模块的数据访问留在自己的 service / domain；共享 schema 不等于共享万能 service。
- Memory / Engineering / Provider 等高权限能力的控制入口可以在前端提供给 Owner，但真正 secret 与执行能力留在后端。
