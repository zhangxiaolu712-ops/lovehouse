## 2026-08-26 · Memory V2 前端正式切流与 Checklist 服务端状态

- `/brain` 与 `/memory` 保留必要浏览、新增、搜索、归档和特殊标记交互，数据层统一通过 Owner-auth `/api/v1/memory/claude/*` 访问 Memory V2；V1 awaken/faded/legacy weight 已退休。

- 全屋搜索的“记忆”来源走 Memory V2，其他日记/语录/纸条/私密模块维持原数据源。

- `brain`、`memories`、canonical V1 不再有生产前端/Bridge reader 或 writer；在切流 read-back 后进入 frozen 状态，暂不 DROP。

## App 入口与门锁（已部署）

- `AuthGate` 位于所有页面之前：新设备先使用 Supabase 邮箱账号登录，之后每次重新打开或刷新使用本机 6 位 PIN。
- Supabase 登录会话保存在设备上；PIN 只在本机保存加盐慢哈希，不上传数据库。
- App 离开前台超过 30 秒会自动回锁，也可点击右上角手动锁定。
- `manifest.webmanifest` 与 `sw.js` 提供手机/桌面安装入口；离线缓存只保存本站程序外壳，不缓存 Supabase 数据。
- 启动时显示最短 1.5 秒的轻量开屏动画；App 图标、登录/PIN 门锁与默认主题统一使用原创“星球玫瑰”极简线条视觉。
- 第一阶段采用单主人模式；旧内容表已有主人 RLS migration 记录，但 2026-08-09 生产复核发现 `brain` 缺 policy、`livingroom` 未启用 RLS、Dreaming 四表仍为 `allow_all`，因此 P0 安全修复尚未完成。
- 已执行的权限变更保存在 `supabase/migrations/20260726170157_secure_owner_only_rls_except_toy.sql`。
- Toy/ADB 链路本轮冻结，`toy_commands` 不在此次 RLS migration 内，原控制策略保持不变。

### 统一 Memory System 第一阶段（代码地基，未部署、未迁移）

LoveHouse 只维护一套记忆规则，GPT MCP 与 Claude MCP 只是固定 actor 的两扇门：

```text
GPT MCP ─────┐
             ├─→ AccessPolicy → MemoryService → MemoryRepository → Supabase
Claude MCP ──┘

MemoryService
├── GPT Memory
├── Claude Memory
├── Shared Memory（仅 approved 可被双方读取）
└── Legacy Pending（默认不进入日常 recall）
```

服务端访问链固定为：`MCP Adapter → 固定 actor → AccessPolicy → MemoryService → MemoryRepository → Supabase`。MCP 参数不提供 namespace 选择器；即使伪造 `space_key`、`space` 或 `namespace`，服务层也会拒绝。

| Actor | 读 GPT | 写 GPT | 读 Claude | 写 Claude | 读 approved Shared | 读 pending Shared | 读 Legacy Pending |
|-------|----------|----------|-------------|-------------|----------------------|---------------------|---------------------|
| GPT | ✅ | ✅ | ❌ | ❌ | ✅ | ❌ | ❌ |
| Claude | ❌ | ❌ | ✅ | ✅ | ✅ | ❌ | ❌ |

第一阶段代码采用未来唯一规范表 `memory_entries` 的 Repository 合约；该表尚未创建，代码没有部署。现有 `brain` 与 `memories` 只保留为未来 Legacy Pending 的来源，不再允许 MCP 继续将它们发展成两套记忆系统。

原有历史正文不会自动进入新系统，也不会默认设为 Shared。下一阶段 migration 必须保留 `original_table`、`original_id`、`original_created_at`、`legacy_source` 与已有可追溯字段，并让所有旧内容先进入不可日常检索的 Legacy Pending。

旧 `20260808174047_memory_namespace_v1.sql` 草稿包含“旧数据默认 shared”的错误逻辑，现已退出 `supabase/migrations/`，仅在 `supabase/retired_migrations/` 留存带强制失败保护的历史副本。它不能进入 Supabase active migration 链。P0 RLS/public exposure 修复继续拆成独立 PR。

### 统一 Memory System 第二阶段（Draft schema，未部署、未迁移）

- V2 migration 新建 `memory_entries`、空间/type 目录、revision、provenance、Shared transition、audit、mutation idempotency 与 ingest candidate 九张规范表。
- `space_key`、`memory_type`、`tags` 保持独立；旧正文不由 migration 读取，Legacy Pending 未来导入必须保留四项原始来源。
- Shared 由 Curator 从确定的 private revision 创建不可变 candidate；只有 Owner 可 approve/reject/revoke，GPT/Claude 仅能读取 approved Shared。
- Curator 通过仅供 Bridge 的固定 RPC 创建 candidate；Owner 通过 `auth.uid()` 固定身份的认证 RPC 决策。AI 不传 actor、owner、space、revision/hash 或权限字段。
- `memory_revisions` 对 Bridge 服务角色只读，只能由历史触发器生成，禁止直接伪造 private revision。
- 数据库提供固定 actor 的 `memory_get/list/recall_gpt|claude` RPC，Bridge Repository 不直接查询正文表；应用层仍保留 AccessPolicy 二次过滤。
- 九表全部启用 RLS；service role 绕过 RLS 的事实由测试显式覆盖，因此不得将服务密钥交给前端。
- `SupabaseMemoryAuditSink` 已实现但未接入生产，Memory 写入仍关闭，`MEMORY_SYSTEM_ENABLED` 仍为 false。
- 验证采用 GitHub Actions 一次性本地 Supabase，不创建付费 Branch、不连接生产项目。详细设计见 `docs/MEMORY_SYSTEM_PHASE2_SCHEMA.md`。

### 统一 Memory System 第三阶段（Draft Runtime，未部署）

- GPT SSE MCP 与 Claude HTTP MCP 已通过固定 actor channel 接入同一个 `MemoryService → Repository → 固定 actor 数据库 RPC` 链路。
- 保存、修订、revision、provenance、幂等和 audit 在同一事务完成；audit 失败会回滚完整 mutation。读取也持久化审计，无法审计时 fail closed。
- service role 不再直接访问 V2 规范记忆表，也不能调用 Phase 2 原始读门/幂等/Curator RPC；只授予 GPT/Claude 对称固定 Runtime RPC。
- 普通 SQL 查询从候选集合开始就排除另一方 private、未批准 Shared 和 Legacy Pending，不依赖查询后的应用过滤。
- 原有 9 个 MCP 工具兼容，新增 `get_memory`、`revise_memory`、`propose_shared_candidate`、`expand_source`；AI 不传 owner/actor/space/revision/hash/request id/权限字段。recall-like 接口默认 summary-first，source 只由显式 `expand_source` 经 fixed-actor Runtime 门与可替换 SourceResolver 展开；Memory core 不依赖 livingroom、Supabase REST path 或浏览器生命周期。
- 当前仍未应用生产数据库、未部署 Bridge、未开启 `MEMORY_SYSTEM_ENABLED`。完整设计与风险见 `docs/MEMORY_SYSTEM_PHASE3_RUNTIME.md`。

## 2026-08-20 · Memory V2 Phase 1 / 2A 生产旁路（未切流）

Phase 1 schema 已由生产 migration `20260820125305_create_memory_v2_phase1` 建立并完成一次性旁路 smoke。该旁路不接管现有 canonical Memory，不读取或迁移 V1 数据，也没有接入 MCP、Chat、前端或生产 Bridge；生产 Bridge 当前仍不注册 `bridge/memory-v2/`。

| 新表 | 职责 | 是否承重 |
|------|------|----------|
| `memory_v2_entries` | owner、固定 private/Shared 空间、当前 revision、currentness 与有上限的召回统计 | 是 |
| `memory_v2_revisions` | append-only 正文、可空事件时间、可选人类/AI 重要性与自由 metadata | 是 |
| `memory_v2_sources` | 可选、可复用的原文快照或 provenance descriptor | 否 |
| `memory_v2_revision_sources` | 确定 revision 与 source 的多对多关系 | 否 |
| `memory_v2_embeddings` | 1536 维、按 revision 保存的可删除/可重建语义索引 | 否 |

Bridge 新增独立 `bridge/memory-v2/` Service/Repository，但没有在 `server.js` 注册。`remember` 只要求正文；owner、GPT/Claude actor 与 private scope 由服务端 facade 固定。Embedding 在正文事务成功后 best-effort 写 sidecar，召回时不可用则回退 PostgreSQL lexical + `pg_trgm`；非 ASCII 查询另以相邻双字覆盖率补足中文插词命中，至少覆盖一半才进入候选。返回通过 `mode=lexical_fallback`、`semantic_error` 显式报告降级；恢复后返回 `mode=semantic`。正常 recall 的 importance 仅作为可调排序信号（AI 70%、human 30%）。Starter Pack 不使用 importance 排序：专用只读 RPC 直接从全部当前可见事实中选择 current revision、active、未 superseded、actor private + approved Shared；inactive/fulfilled/cancelled commitment 与 revoked Shared 均排除。它依次返回有效承诺（最多 4）、最近 revision（最多 8）、从剩余完整合格池随机抽取的盲盒（最多 3），三类去重且没有 recent-pool 预截断；Service 只按该顺序执行总数软上限 15 和 1600 estimated-token 硬截断，不自动展开 source。

## 2026-08-25 · Engineering Memory Foundation V1（本地待审，未部署）

Engineering Memory 是现有 Memory V2 内部的独立 `engineering` space，不是生活记忆分类，也不进入普通 `recall`、`wake_up`、Starter Pack 或 Chat 自动召回。它复用 `memory_v2_entries`、append-only revisions、sources 与 revision-source links；`subject_key` 是同一 owner 下工程事实的稳定身份。

```text
trusted engineering actor (GPT / Claude / Codex / Owner)
  → EngineeringMemoryService fixed-actor facade
  → memory_v2_engineering_* RPC
  → space_key=engineering + subject_key + current revision + source evidence
```

- `upsertEngineeringFact`：subject 不存在时创建 Entry/revision 1；存在且内容或显式 metadata/source 变化时追加 revision；相同正文且没有显式变化时 no-op。

- `openEngineeringFact`：返回 Entry 与 append-only history，以及不含 `quote_text` 的 source descriptors；原文只能用 `expandEngineeringSource` 显式展开。
- `archiveEngineeringFact` / `restoreEngineeringFact`：只允许 Owner soft archive/restore，不物理删除 revision/source。
- Engineering V1 不写 embedding；现有 backfill 仍只遍历 GPT/Claude ordinary recall，因此不会误扫 Engineering。
- `gpt`、`claude`、`codex`、`owner` 可通过独立工程 facade 读写 Engineering；普通 Memory façade 仍只接受 GPT/Claude，Codex 不获得任何 private Memory 权限。
- Owner Client API 位于 `/api/v1/engineering-memory*`（Nginx 去掉 `/api` 后为 Bridge `/v1/*`），继续复用 Owner bearer 验证；客户端不能提交 actor/space/permissions。
- 7-tool MCP surface 未增加 Engineering tool。
- `/engineering` 是独立 Owner 工作区；前端只通过 Supabase session bearer 调用 `/api/v1/engineering-memory*`，不直连 Memory V2 表或 service role。
- 分类配置集中在 `engineeringCategories.js`；列表按 `category → component → subject_key` 展示，未知 category 与未完整分类记录仍正常显示和保存。
- 页面支持新增、按稳定 subject 修订、soft archive/restore、完整 revision history 与显式 source evidence 展开。
