# GitHub 审阅与部署流程

日期：2026-08-09

## 做了什么

- 将“每轮开发先推 GitHub、人工查看后合并、部署单独确认”写入共同开发规则。
- 明确每轮必须记录 `已提交 / 已合并 / 已部署` 三种独立状态。
- 明确低风险 UI/文档与数据库、权限、Bridge、VPS、Toy 等高风险改动必须拆分 PR。

## 为什么

修整过程中经常会继续提出新需求。如果没有明确的交付闭环，注意力转移后容易遗漏推送、合并或部署。本规则让每轮都有可追踪的停靠点和人工确认环节。

## 修改文件

- `PROJECT_RULES.md`
- `docs/changes/2026-08-09_GitHub审阅与部署流程.md`

## 数据库、环境变量与生产影响

- 无数据库、环境变量、权限、VPS、Cloudflare 或 Toy 变更。
- 仅更新项目协作规则，不执行合并或部署。

## 验证与回滚

- 运行 `git diff --check` 检查文档格式。
- 回滚方式：撤销本次文档提交，不影响程序与数据。

## 下一步

- 当前界面任务通过 Draft PR 提交；由小婷在 GitHub 查看后决定是否合并。
- PR 合并后再单独确认生产部署，并补线上验证结果。
