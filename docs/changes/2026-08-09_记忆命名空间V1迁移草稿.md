# 记忆命名空间 V1 迁移草稿

日期：2026-08-09

状态：`READY_FOR_REVIEW` / `DATABASE_NOT_APPLIED` / `NO_PROD_CHANGE`

## 做了什么

- 新建独立分支 `agent/memory-namespace-v1`。
- 使用固定版本 Supabase CLI `2.113.0` 生成 migration 骨架。
- 设计一张 `memory_spaces` 表，预置 `claude`、`gpt`、`shared` 三个记忆空间。
- 档案字段包括显示名、自我描述、说话方式、记忆策略、扩展 JSON、启用/归档状态与更新时间。
- 为 `brain`、`memories`、`window_summaries`、`memory_candidates`、`active_threads`、`dream_runs` 增加统一 `space_key` 设计。
- 旧数据只默认进入 `shared`，不根据作者字段自动认领。
- migration 内置前置安全检查和迁移后自检；任何检查失败都会由事务整体回滚。

## 为什么这样做

GPT 与 Claude 需要两套独立记忆体，但复制整套表会导致结构漂移和重复维护。一套引擎加命名空间既能隔离双方，又能保留共同记忆，并方便未来增加其他 AI。

当前数据库的 Dreaming 表仍存在 `public allow_all`，`brain` 也尚未具备可用主人策略。命名空间不能代替访问控制，所以本 migration 明确依赖 P0 owner-only RLS，并在不满足条件时主动停止。

- **没有执行 production SQL。**

## 权限设计

- `memory_spaces` 开启 RLS。
- `anon` 无任何权限。
- 登录的唯一主人可读取全部空间，只能更新档案内容字段，不能从前端新增或删除空间。
- `service_role` 仅供未来受限 Bridge 使用，绝不进入前端。
- AI 的真实隔离必须由后续 MCP 工具按自身身份固定过滤 `space_key`，不能让调用者自由传入任意空间。

## 回滚方案

如果 migration 在未来已应用且尚未写入专属空间数据，可在备份后执行：

```sql
begin;

alter table public.brain drop column if exists space_key;
alter table public.memories drop column if exists space_key;
alter table public.window_summaries drop column if exists space_key;
alter table public.memory_candidates drop column if exists space_key;
alter table public.active_threads drop column if exists space_key;
alter table public.dream_runs drop column if exists space_key;
drop table if exists public.memory_spaces;

commit;
```

如果已经产生 Claude/GPT 专属数据，禁止直接执行上述回滚；应先导出并将专属记录映射回 `shared`。
