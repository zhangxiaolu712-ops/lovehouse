# 2026-08-23 原生 App 产品边界与工程问答

## 状态

本文件记录 2026-08-23 在原生 Android App 开工前，由小婷确认的产品边界与工程决策。

当前阶段仅做需求归档，不代表对应功能已经施工、测试或部署。

## 一、LoveHouse 的产品定位

- 官方 App 仍然是日常高频聊天的主要入口，LoveHouse Chat 是完整但备用的聊天入口。
- LoveHouse 的目标不是复刻 ChatGPT / Claude 官方 App，而是成为全能的个人 AI 空间，补全官方 App 不具备或不稳定的能力。
- 官方平台存在模型下架、灰度测试、额度变化、账号风险等不可控因素，因此 LoveHouse 必须保留独立长期聊天和切换模型的能力，作为可控退路。
- LoveHouse 不应依赖某一家模型厂商作为地基；Memory、档案、工具、工作流、VPS 与客户端能力应独立于具体 Provider。
- Web 与原生 App 功能原则上基本等价，但布局分别针对大屏/横版与手机/竖版优化；特殊布局允许端侧独占。

## 二、聊天与多模型

- LoveHouse 内需要支持真正的长期聊天，而非仅查看官方 App 记录。
- 同一个聊天窗口允许中途切换底层模型，类似官方 App 内切换模型；窗口历史属于 LoveHouse，不绑定死某个模型。
- 第一批模型方向：OpenAI、Anthropic/Claude、xAI/Grok、Google/Gemini、DeepSeek；架构需允许未来继续增加 Provider。
- API 聊天应尽量使用各厂商提供的提示词缓存/缓存计费机制，目标是减少重复上下文成本；不要求所有 Provider 第一版一次实现完。
- 官方订阅仍具有明显成本优势，因此 LoveHouse 不以强制替代官方 App 为目标。

## 三、AI 身份与底层模型分离

- 用户希望喜欢的 AI 尽可能长期连续存在；底层模型可能因为下架、更新或平台变化而更替。
- 因此数据库与应用层应区分“AI 身份”和“底层模型 Provider/Model”。
- 更换底层模型时，允许在用户选择下继续承接原 AI 的 Memory、人格、关系历史与窗口状态。
- 正常情况下用户不会频繁切换长期使用的模型；喜欢且稳定的模型会持续使用到出现问题或下架。

## 四、聊天记录生命周期

用户当前倾向：

- 近 3 天：Supabase 保存完整聊天原文。
- 3 天以前：转为压缩记录。
- 1 个月以前：先将已有压缩记录进一步压成更短的一两句长期痕迹，再额外保留 1 个月；若这段期间没有新的变化或再次被引用，则到期删除。
- 已确认采用“双机制”：平时自动把值得连续的内容提炼进 Memory / 原文档案；同时允许用户对特别舍不得的窗口或消息手动标记“珍藏”，珍藏原文永久保留，不参加一个月清理。
- “珍藏”同时支持整窗口与单条/多条消息两个粒度。
- 这样既避免普通聊天无限堆积，又能保住真正重要的原文。
- 日常聊天在 3 天后采用“浓缩版对话”压缩：尽量保留谁说了什么、AI 如何回应、互动中的转折与变化，只压掉重复和低价值闲聊。
- 工程聊天则更适合“事件/决策摘要”式压缩：保留做了什么、为什么、结果、风险和后续。
- 原文压缩后进入回收期，默认 5 天后真正删除；该天数应允许用户自定义。
- “淡忘”采用两阶段：先短压缩再留 1 个月，只有无后续变化时才真正删除。
- 具体压缩格式与定时任务实现细节仍需施工前确认。

## 五、工具与工程权限

- Codex 与 Claude Code（CC）默认可以获得工程施工能力。
- 不把工程权限硬编码成只有 Codex/CC；未来出现更合适的工程模型时，可以由用户授权。
- 其他普通聊天模型默认不自动获得高风险工程权限，用户可以额外授权。
- Codex / CC 这类具备工程能力的大模型，在 LoveHouse 内采用“双线程”：一个主聊天线程，一个工程聊天线程。
- 主聊天线程默认只读，不直接修改项目；用户切换“工程模式”时，跳转到独立工程线程，在工程线程中获得可写工作区、测试、Git 等工程能力。
- 主聊天与工程聊天需要保持同一 AI 身份下的关联，但会话、权限和施工状态分离，避免普通聊天误触发真实改动。
- 同一 AI 身份允许存在多个聊天窗口；这些窗口不是彼此失忆的孤岛，而是归属于同一个更高层的“聊天项目/聊天文件”。
- 同一聊天项目内的多个窗口共享可检索的原文、近期对话摘要、长期记忆与项目状态；用户可在多个窗口间任意切换并继续话题，不要求重新解释背景。
- 窗口只保存局部话题、当前滚动/会话状态、主聊天或工程模式等轻量状态；共享历史只存一份，避免重复数据。
- 模型上下文层不应每轮机械塞入全部历史，而应组合“当前窗口局部上下文 + 最近跨窗口内容 + 更早摘要/Memory/项目状态”按需构建上下文。
- 多个窗口可以整理到同一个聊天项目中，类似项目空间；其目标是“窗口可以多个，历史只有一份；线程可以多个，身份与记忆只有一个”。
- Codex / CC 的 reasoning / Thought process 与工具事件属于运行过程数据，默认不进入“全文收藏”、长期聊天原文、Memory 或珍藏正文。
- “全文收藏”只保存用户可见的正式聊天正文与用户明确珍藏的消息/窗口内容；如需保留工程过程，仅保存轻量元数据（例如耗时、步骤数、调用过哪些工具、测试结果），不保存冗长 reasoning 全文。
- reasoning / 工具事件可以在工程窗口中临时查看、折叠和分层浏览，但应采用更短的独立保留周期或会话级临时存储，避免长期膨胀。
- Memory、Supabase、GitHub、LoveHouse、Galatea Garden 等日常/小型工具调用原则上无需每次确认。
- VPS 等大工具/高影响施工应在执行前询问用户。
- “哪些 VPS 动作属于必须确认”仍需进一步细化，不能在需求不明确时自行猜测。

## 六、需求歧义施工规则

- 如果用户需求存在两种以上合理理解，且不同理解会造成不同代码/部署结果，必须暂停并向用户提问。
- 不允许在已经意识到“没听明白”的情况下继续盲目施工。
- 数据库、部署、OAuth、域名、删除/迁移、生产配置等高影响操作，只要关键意图存在歧义就必须停。
- 小型、低风险且已有明确母版/规范可推导的实现细节可以自行处理，避免把所有细节都反问用户。

## 七、离线与手机本地缓存

- App 使用手机自身网络；正常情况下用户手机长期有网。
- 断网时：不能刷新、不能聊天，但已经缓存到手机上的内容仍应可查看。
- 文字可以较充分地保留本地缓存。
- 图片本地缓存倾向只保留最近约 2–3 天，之后按需重新下载。
- 用户手机本地存储约 512GB，因此文字缓存容量不是主要约束。
- 第一版不需要为了极端离线场景实现复杂的离线冲突合并系统。

## 八、附件与云存储

- 模型不拥有附件原件；原文件应存放在用户控制的云端/对象存储，模型只获得必要的访问能力。
- 已讨论 Cloudflare R2（当前认知容量约 10GB）作为候选。
- 普通临时附件可以设置自动删除；重要档案需要支持固定保留。
- 手机端图片只做短期缓存。
- 文件类长期云存储平台仍需后续比较/确认，不在本轮直接定死。

## 九、通知

- 原生 App 必须支持主动手机通知/弹窗。
- 典型场景：Codex 工单完成、任务结束、小客厅新消息、AI 主动留言、自动任务完成等。

## 十、成本与额度显示

- 不设置“达到金额后突然硬停聊天”的默认行为，以免破坏体验。
- 达到成本/额度阈值时应通知用户。
- 工作台需要显示 token 与估算成本。
- API 渠道显示实际/估算 API 消耗以及缓存节省情况。
- Codex CLI、CC CLI 等订阅渠道应尽量显示订阅额度/剩余额度，而不是伪装成 API 金额。

## 十一、官方 App 内容进入 LoveHouse

- 不为了抓取官方 App 全文而对抗官方平台的安全边界。
- 如果未来官方提供合适、允许的自动化接口，可以正规接入 LoveHouse。
- 如果没有自动化能力，则允许官方 App 内的模型通过 LoveHouse MCP 手动/主动保存值得长期保留的内容。
- 目标是保存连续性所需的重要内容，而不是强制复制官方平台完整聊天数据库。

## 十二、Web 与 Android UI

- Android 原生 UI 不复刻现有网页视觉，目标是更像真正的手机 App。
- Web 保留大屏、横版、展览式布局的优势；Android 采用竖屏、单手操作和原生交互。
- 两端共享数据、API、信息架构和视觉语言，但不机械共享布局。
- 视觉概念可先用 Web 快速原型验证，再根据手机交互重新翻译成 Jetpack Compose；不是把 HTML 机械转换成 Compose。

## 十三、当前推荐技术方向（尚未施工）

- Android：Kotlin + Jetpack Compose。
- App 只依赖 LoveHouse 自己稳定的客户端 API，不直接绑定某一家模型或数据库实现。
- Provider Adapter 支持替换 GPT / Claude / Gemini / Grok / DeepSeek 等模型。
- 工具层独立于聊天 Provider。
- Bridge 继续保持薄，不重新吞入 Memory、Provider、业务状态等职责。

## 十四、仍需后续逐项确认的问题

1. 第一版原生 App 的确切功能范围。
2. 3 天后聊天压缩已确认：日常聊天用浓缩版对话；工程聊天用事件/决策摘要。
3. “珍藏”已确认同时支持整窗口与单条/多条消息。
4. VPS 工具中哪些具体动作必须弹确认。
5. R2 / Supabase Storage / 其他对象存储的长期文件分工与自动删除周期。
6. Android 推送具体采用哪套基础设施。
7. 多 Provider 缓存支持的实施顺序。
8. AI 身份切换底层模型时，Memory/人格/上下文继承的具体规则。

## 十五、记忆与项目资料边界

用户再次明确：

- LoveHouse Memory 记忆库只用于生活、关系、事件、原话、体验和相关连续性内容。
- 工程讨论、技术决策、工作进度、项目需求与施工问答不要写入生活 Memory。
- LoveHouse 工程信息应进入项目文档/项目文件夹，例如本文件，而不是 Memory V2。

该边界适用于后续工程讨论与原生 App 施工。

## 十六、LoveHouse 项目文件的定期清理与理念更新

- LoveHouse 项目文件夹不能只积累不整理；需要定期审查和清理。
- 旧文档、旧方案、旧理念如果已经与当前方向不一致，应明确标记为过时、归档或删除，避免后续 AI 把历史方案误当成现行规则。
- 仍有审计/回滚价值的历史记录优先归档，不与当前入口文档混放。
- 当前规则、架构、部署状态应尽量收敛到少量明确入口；历史变更继续保留证据，但不应承担当前指导职责。
- 后续适合单独建立“项目文档收口/清理”任务，不在原生 App 需求讨论时顺手大规模移动目录。
