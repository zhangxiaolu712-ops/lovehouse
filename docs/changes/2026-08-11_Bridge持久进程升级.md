# 2026-08-11 Bridge 持久进程升级

## 做了什么

VPS bridge 的聊天架构从"每条消息 spawn 一个 claude 进程"升级为"一个持久 Claude 进程 + stream-json 双向通信"。

新增 `bridge/claudeProcess.js` 模块：
- `sendMessage(message, systemPrompt, callbacks)` — 向持久进程发送消息，通过回调流式返回文本/思考链/完成/错误
- `resetSession()` — 杀掉当前进程（下次发消息时自动重启），用于清除对话
- `getStats()` — 返回进程状态（alive/busy/pid），接入 `/health` 端点

进程通信协议：
- 启动参数：`claude --input-format stream-json --output-format stream-json --verbose --system-prompt "..."`
- 输入格式：`{"type":"user","message":{"role":"user","content":"..."},"session_id":"default","parent_tool_use_id":null}`
- 输出事件：`system`（初始化）→ `assistant`（文本/思考链）→ `result`（完成）或 `error`

server.js 改动：
- `/chat` 端点：不再 spawn 新进程，改为调用 `claudeSend()`，通过回调转发 SSE 事件
- `/reset` 端点：调用 `resetSession()` 杀掉持久进程
- `/health` 端点：新增 `claude_process` 字段显示进程状态
- 移除 `child_process` 和 `chatContext.js` 的导入

前端 chatService.js 改动：
- `streamBridge` 新增 thinking 事件解析，bridge 模式现在也支持思考链展示

## 为什么

之前每条消息 `claude -p <prompt>` 启动一个全新进程，有三个问题：
1. **无上下文**：每轮都是全新对话，需要手动拼接历史（chatContext.js 的 30 条方案）
2. **无缓存**：每轮都要从头读取上下文，浪费订阅额度
3. **无思考链**：`-p` 模式拿不到 thinking blocks

持久进程模式解决以上全部：
1. CLI 自动管理对话上下文，不需要手动拼历史
2. 同一进程内连续对话享受 prompt caching（相同前缀 5 分钟内约 10% 成本）
3. stream-json 输出包含 thinking blocks（如果 CLI 支持导出）

## 设计决策

- **独立模块**：`claudeProcess.js` 可以整个替换，不影响 server.js 其他功能
- **懒启动**：进程在第一条消息时才启动，不是服务器启动时
- **杀进程重置**：清除对话 = kill + 下次自动重启，简单可靠
- **并发拒绝**：同一时间只处理一条消息，第二条返回 busy（个人应用，单用户）
- **断连不杀进程**：客户端断开时进程继续完成当前回复，保持上下文完整
- **chatContext.js 保留**：文件不删，以后需要可以切回

## 修改了哪些文件

- `bridge/claudeProcess.js` — 新文件，持久进程管理模块
- `bridge/server.js` — 导入换为 claudeProcess，重写 /chat 和 /reset 端点，/health 加进程状态
- `src/modules/chat/chatService.js` — streamBridge 新增 thinking 事件支持

## 验证

- `npm run build` 通过
- bridge 为 Node.js 服务端，需在 VPS 拉取后验证

## 风险

- 中风险：CLI `--input-format stream-json` 在 VPS 上的 Claude CLI 版本可能不支持，需确认版本
- 低风险：如果 stream-json 模式不可用，可以回退到旧方案（恢复 chatContext.js 导入和 spawn 逻辑）
