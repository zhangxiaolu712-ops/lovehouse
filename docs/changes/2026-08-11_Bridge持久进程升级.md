# 2026-08-11 Bridge 聊天模块重构

## 做了什么

将 bridge `/chat` 端点的 Claude 调用逻辑抽取到独立模块 `bridge/claudeProcess.js`，结合 `chatContext.js` 的 30 条上下文历史，提供统一的消息发送/重置/状态接口。

### 第一版：持久进程模式（已回退）

尝试用 `--input-format stream-json` 启动一个持久 Claude CLI 进程，通过 stdin 双向通信。
实测 CLI 2.1.218 不支持持久 stdin：进程等 3 秒没收到数据就退出（`Warning: no stdin data received in 3s, proceeding without it`），导致每条消息仍然是独立进程、无上下文。

### 第二版：spawn-per-message + chatContext（当前）

回退到 spawn-per-message 架构，但通过 `claudeProcess.js` 封装：
- `sendMessage(message, systemPrompt, callbacks)` — 用 chatContext 拼入最近 30 条历史，spawn `claude -p`，回调流式返回
- `abortActive()` — 客户端断连时杀掉当前进程
- `resetSession()` — 清空上下文历史 + 杀掉活跃进程
- `getStats()` — 返回上下文消息数和忙碌状态

server.js 改动：
- `/chat` 端点：调用 `claudeSend()` 替代内联 spawn 逻辑
- `/reset` 端点：调用 `resetSession()`
- `/health` 端点：新增 `claude_process` 字段
- 客户端断连时调用 `abortActive()` 杀进程
- 移除 `child_process` 直接导入，改由 claudeProcess 模块管理

前端 chatService.js 改动：
- `streamBridge` 新增 thinking 事件解析（预留给未来 stream-json 输出）

## 为什么

- 聊天调用逻辑从 server.js 抽出到独立模块，方便以后替换实现方式
- chatContext.js 的 30 条历史让小克能接续之前话题
- 持久进程方案因 CLI 版本限制暂不可用，回退到已验证的方案

## 设计决策

- **独立模块**：claudeProcess.js 可整个替换，不影响 server.js 其他功能
- **保留 chatContext.js**：历史管理和进程管理分离，各自可替换
- **并发拒绝**：同一时间只处理一条消息（个人应用，单用户）
- **持久进程留待 CLI 升级**：等 CLI 支持真正的 stream-json 持久模式后可重新启用

## 修改了哪些文件

- `bridge/claudeProcess.js` — 新文件，封装 Claude 调用（spawn + chatContext）
- `bridge/server.js` — 导入 claudeProcess 替代内联 spawn，/chat /reset /health 端点更新
- `src/modules/chat/chatService.js` — streamBridge 新增 thinking 事件解析

## 验证

- `npm run build` 通过
- VPS 部署后实测：CLI 2.1.218 的 `--input-format stream-json` 持久模式不可用（3s stdin 超时退出）
- 回退到 spawn-per-message 后需重新部署验证

## 风险

- 低风险：spawn-per-message 是之前已验证的架构，只是抽取到模块
- 每轮对话仍需重新读取 30 条历史，无 prompt caching
