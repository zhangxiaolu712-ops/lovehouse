## 1. 资料归属

### GitHub / VPS 长期保留

只保留“现在如何继续施工”所需的稳定资料：

- `PROJECT_RULES.md`：共同开发规则与安全边界。
- `docs/00_工程边界与资料索引.md`：本文件，说明资料应该放在哪里、去哪里找。
- `docs/02_当前架构.md`：当前架构入口；只描述当前主干，不承担完整历史。
- `docs/06_待开发列表.md`：当前规划 / 未完成项；完成后及时收口，不把阶段流水永久堆在这里。
- `docs/changes/`：代码改动的 Git 证据链。保留与 commit/PR 对应的 change record，但不再把它当作跨模块“当前状态数据库”。
- 与现存承重模块直接对应的架构合同 / 接口文档。

### Engineering Workspace 长期保存

以下内容以稳定 `subject_key` 为身份，变化时追加 revision：

- 当前生产事实：release、PM2、Nginx、端口、Runtime、Memory、部署方式。
- 历史工程状态：旧日期、旧版本、旧决策及其后来如何被修订。
- 架构决策与边界变化。
- 部署记录、故障、错误经验、回滚经验。
- 来源证据：commit、PR、文档路径、release、配置位置、验收记录。
- 多个文档描述同一工程事实时，不创建多条“文件记忆”；合并到同一 subject 的 revision history。

### 不进入 Engineering Workspace

- 生活记忆、亲密互动、个人原话与关系轨迹。
- 纯视觉原型 HTML 的每个中间版本，除非它本身代表一个需要长期追踪的工程决策。
- 重复 release 快照本身。它们只可作为 source evidence，不作为一条条工程事实灌入。

## 3. 来源优先级

发生冲突时按以下顺序判断“当前事实”：

1. **当前 VPS 实测状态**：进程、监听端口、Nginx、release、实际代码。
2. **当前 `origin/main` 代码与已合并 change record**。
3. **官方 App 文件库里的高密度基线 / 审查 / 总账文件**。
4. **旧 checkout、旧 worktree、历史 release 内的文档**：默认只作为历史证据。

任何旧文档写着“待做 / 未部署 / 当前状态”时，都必须和更晚的代码、release、线上实测核对，不能直接当 current。
